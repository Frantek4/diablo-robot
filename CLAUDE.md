# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Context

This is a **single-server, non-commercial** bot built for a personal community (Club Atlético Independiente fans). It will never run in more than one Discord server, so:
- No multi-guild handling: no guild_id guards, no per-guild state, no guild lookup loops
- No copyright or scraping concerns: web scraping and RSS aggregation are for community use only
- No need to prepare for scenarios that only matter at scale (rate limits, sharding logic, multi-tenant isolation, etc.)

## Running the Bot

```bash
python main.py
```

Requires MongoDB running (see `DATABASE_URL` in `.env`). All required environment variables are validated at startup in `main.py`.

## Architecture

**Diablo Robot** is an async Discord bot (`discord.py`) for Club Atlético Independiente's server. It tracks football fixtures, posts live match commentary, aggregates news/social media, and includes an AI-powered music agent.

### Layer Structure

- **`main.py`** — Entry point: validates env vars, creates bot, starts run loop
- **`config/settings.py`** — Pydantic BaseSettings loading all env vars; `config/database.py` — MongoDB singleton
- **`bot/client.py`** — `DiabloRobot` class; `setup_hook()` loads all cogs/commands/listeners/schedulers; `on_ready()` starts scheduled tasks. **Cada comando declara en qué canales se lo puede usar** (ver `bot/config/command_access.py`); `on_message` resuelve el comando y solo lo invoca si el canal está habilitado.
- **`bot/commands/`** — Prefix commands (`!cmd`); admin-only ones check guild permissions
- **`bot/scheduled/`** — Scheduler cogs with a `tasks.loop` started via `start_scheduled_job()` in `on_ready()`
- **`bot/cogs/`** — Stateful Discord cogs (fixture event creation, event lifecycle, live match commentator)
- **`bot/listeners/`** — Event handler cogs (reactions, event announcements, music agent)
- **`bot/ui/`** — Discord UI components (buttons, views) used by cogs and listeners
- **`bot/config/messager.py`** — Centralized message dispatcher; holds typed references to all channel objects; initialized in `on_ready()` via `init_messager(bot)`
- **`data_access/`** — DAO classes wrapping raw PyMongo queries; one DAO per MongoDB collection
- **`models/`** — Plain dataclasses; `fixture.py` handles emoji formatting and change detection
- **`integrations/`** — Web scrapers (BeautifulSoup + aiohttp) for Promiedos, Olé, TycSports, DobleAmarilla, Twitter (API GraphQL de X, `x_api.py`), YouTube RSS, Instagram

### Data Flow

1. **Fixture check** (`bot/scheduled/fixture_check.py`, 1h loop): scrapes Promiedos → upserts into `fixtures` collection → `FixtureEventCreator` cog creates/updates Discord scheduled events and announces changes to `#announcements`

   Cada partido que se agenda en Discord se agenda también en un **Google Calendar** (`integrations/google_calendar.py`, vía service account), para que la gente lo tenga en el celular sin depender de Discord. Se agenda **el partido, no el evento de Discord**: el de Discord arranca 15 min antes para que la gente se junte, el del calendario arranca a la hora del partido y dura 2 h. Se escribe **solo cuando el bot tocó el evento de Discord** (lo creó, o lo editó porque `get_changes` detectó cambios); una vuelta del loop sin novedades no llama a Google. No se guarda ningún id en Mongo: el id del evento de Google sale del `match_id` de Promiedos (`"diablo" + sha1`), así que el mismo partido siempre pisa el mismo evento y escribir es idempotente. Es opcional — sin `GOOGLE_CALENDAR_ID` o `GOOGLE_SERVICE_ACCOUNT_FILE` el espejo no corre — y un error de Google se loguea pero nunca rompe el evento de Discord. El comando **`!calendario`** (`bot/commands/calendario.py`) postea en el canal donde lo corras el embed con el que la gente se suscribe, pensado para fijarlo y no tocarlo más: un botón link a Google Calendar y otro, con `custom_id` fijo registrado vía `bot.add_view()`, que contesta ephemeral con el `.ics` para iPhone/Outlook — por eso la vista sobrevive los reinicios.
2. **Live match**: `CommentatorScheduler` (`bot/scheduled/commentator_scheduler.py`, 1min loop) queries DB for the next match; when ≤30 min away, delegates to `LiveMatchCommentator` cog (`bot/cogs/live_match_commentator.py`), which spawns an `asyncio.Task` that polls the Promiedos game-center API every 30s and posts events to `#comentador`
3. **Event lifecycle**: `EventLifecycleManager` cog (`bot/cogs/event_lifecycle_manager.py`, 5min loop) announces Discord scheduled event starts (with voice invite) and force-ends overdue active events
4. **Post-match discussion**: `EventEndForumPoster` listener (`bot/listeners/post_match_discussion.py`) opens a forum thread in `FOOTBALL_FORUM_ID` when a Discord scheduled event ends
5. **News** (`bot/scheduled/news_check.py`, 1h loop): scrapes Olé/TycSports/DobleAmarilla → deduplicates via `news` collection → posts to `#prensa` or `#club` channel
6. **Social media** (`twitter_check.py`, `youtube_check.py`, `instagram_check.py`): fetches RSS/scrapes → posts new entries to configured channels

   Twitter **mira la home "Siguiendo" de la cuenta del bot una vez por vuelta** (`HomeLatestTimeline`) y postea sólo lo de las cuentas que están en la tabla de `influencers`. No va cuenta por cuenta: una vuelta es un solo pedido —el mismo que hace cualquiera que abre la app—, en vez de una ronda de visitas a perfiles que ninguna persona hace cada hora. La lista de qué se lee la lleva X (a quién sigue la cuenta) y la de adónde va cada tweet la lleva Mongo (canal y descripción de cada influencer); el cruce es por el autor que aparece en la home, sin distinguir mayúsculas, así que el RT de una cuenta de la tabla sale por el canal de esa cuenta, con el tweet original y su link (y así se deduplica solo si dos cuentas retuitean lo mismo). Lo de cuentas que se siguen pero no están en la tabla, y los promocionados, se ignoran; las desconocidas se muestran en `!twitter`. Por eso **`!nuevo_twitter` sigue la cuenta desde la del bot y recién después la anota** (ver más abajo).

   Va contra la **API GraphQL de X directo**, sin Nitter. Antes había una instancia propia de Nitter en Docker, y se abandonó porque además de caja negra era una caja que no se podía tocar: su `rateLimitError()` (`apiutils.nim`) convierte en el mismo cartel un challenge de Cloudflare, una cuenta bloqueada, el rate limit de verdad, un 404 transitorio y cualquier falla de red del Pi —el más común era su pool de conexiones reusando sockets que X ya había cerrado—, y la causa real sólo se podía adivinar leyéndole el log al contenedor. De Nitter se absorbió en Python (`integrations/x_api.py`) lo que hace al pedido: bearer y blob de features de `consts.nim`, los headers de una sesión de cookies de `apiutils.nim` y la firma `x-client-transaction-id` de `tid.nim`. Lo que **no** se trajo es su manejo de errores. Tampoco se usan librerías de terceros: `twikit` está abandonada y rota por el cambio de la firma, y `twscrape` está mantenida pero se traga las fallas igual que Nitter, reintenta y rota cuentas sola.

   **El queryId de la home no está en Nitter**, que nunca leyó una home. Lo busca el bot en el JavaScript que sirve x.com (`discover_home_query`): baja `x.com/home` con las cookies —un documento, lo que pide cualquier navegador, porque el HTML de deslogueado no trae las queries de la home—, recorre los bundles del CDN hasta encontrar `operationName:"HomeLatestTimeline"` y de ahí saca el `queryId` y las `featureSwitches` que declara la propia operación. El blob de features se arma con esa lista: el valor sale del blob de Nitter si lo conoce, y si no `true` salvo una lista corta de las que van en `false` (X sólo falla cuando una feature **falta**, no por el valor). Cuesta decenas de pedidos al CDN, no a la API, así que el resultado se guarda en `twitter_state` y **sólo se vuelve a buscar cuando X rechaza el pedido** (400, 404 o "features cannot be null"): se borra y la vuelta siguiente lo redescubre, no en el acto, para no mandarle a X un segundo pedido justo después de uno que rechazó. Si X rechaza también el recién descubierto (`home_query_verified` todavía en falso), buscarlo de nuevo va a dar lo mismo: lo que cambió es la forma del pedido, y eso es `ClientOutdated`, que frena. Si al bajar `x.com/home` X manda al login, la sesión venció: `AccountFlagged` de sesión, ahí mismo, antes de tocar la API. El pedido va por POST con el cuerpo en JSON, como lo hace la web.

   **Cada respuesta se mira cruda y dice qué pasó** (`_check()` en `x_api.py`): una página de Cloudflare, los códigos de sesión muerta (32, 89, 239, 353) y los de cuenta bloqueada o suspendida (326, 37, 64) son `AccountFlagged`, que apaga el scaneo hasta un `!twitter reanudar` a mano; el 429 o el código 88 son `Throttled` con la hora de reposición que manda X; un queryId rechazado es `Throttled` con `stale_query` (ver arriba); y una excepción de `aiohttp` es `Unreachable`: el pedido nunca llegó a X, así que no corre backoff y se sigue al ritmo normal. Eso último es justo lo que Nitter no permitía distinguir. Si la home trae entradas de tweets pero el parser no puede leer ninguna, es `ClientOutdated` ("actualizar el parser") y no un "no hay nada nuevo".

   **La firma** `x-client-transaction-id` sale como la saca Nitter: no se parsea x.com, se baja cada hora el diccionario público de pares (verificación, clave de animación) de `fa0311/x-client-transaction-id-pair-dict` en GitHub y se calcula con un sha256 sobre método, path y hora. Si GitHub no contesta y no hay pares en memoria, es `Unreachable`: no salió ningún pedido a X. **El parseo** (`integrations/twitter.py`) está portado de `parser.nim` y recortado a lo que lleva un embed; lee las dos formas de tweet que sirve X (la vieja con todo en `legacy`, y la V2 con `details`/`url_entities`/`media_entities`). Se piden 40 tweets por vuelta para que la página cubra las hasta dos horas y media entre vuelta y vuelta.

   Los headers son los de una pestaña de x.com, con el User-Agent del navegador del que salieron las cookies (`X_USER_AGENT`) y **sin** los `sec-ch-ua` que manda Nitter: son de Chrome, y con cookies de Firefox serían una contradicción. La sesión se saca de Firefox con `tools/x_session.py --username <cuenta>` (lee `cookies.sqlite` en modo inmutable) y queda en `~/.config/diablo-robot/x-session-<cuenta>.json`, fuera del repo; loguearse por código dispara captchas, así que no se hace nunca.

   **El ritmo**: la vuelta se agenda sola cada 45-145 min, sólo de 08:00 a 23:00, y la primera se agenda como cualquier otra (reiniciar no compra lecturas). X manda `x-rate-limit-*` en cada respuesta; si lo que queda está por debajo de un colchón (10 pedidos o un cuarto de la ventana) no lee, no avisa, y agenda la vuelta para unos minutos después de la reposición. Backoff de 1/2/4/6 h por falla seguida con un aviso por episodio. El estado —freno, backoff, última ventana de rate limit, queryId y features de la home, y qué vio la última vuelta— va a Mongo (`twitter_state`, vía `SocialStateDAO`). **`!twitter`** muestra todo en `#robot-devil`; **`!twitter detener [motivo]`** y **`!twitter reanudar`** funcionan igual que los de Instagram.

   **Instagram usa el mismo diseño: la home, una vez por vuelta.** `integrations/instagram_api.py` hace el mismo pedido que la web logueada (`POST /api/v1/feed/timeline/`, con `x-ig-app-id`, `x-csrftoken` y las cookies) y `integrations/instagram.py` postea sólo lo de las cuentas de la tabla, cruzando por el autor sin distinguir mayúsculas; las publicidades (`ad_id`/`injected`) se descartan y los sugeridos caen solos porque no están en la tabla. La home de Instagram no es cronológica, así que los posts se ordenan por `taken_at` antes de postear, y lo viejo lo frenan el corte de 7 días y la deduplicación. Mismo ritmo que Twitter: cada 45-145 min, de 08:00 a 23:00. Lo que cambia es el backoff: Instagram **no publica ningún contador** —no dice cuánto margen queda ni cuándo se repone, sólo avisa cuando ya marcó la cuenta—, así que el reloj es a ciegas y por eso largo (`_BACKOFF_HOURS`, 2/6/12/24 h). El endpoint de la home salió de las candidatas de `tools/probe_feeds.py`; si Instagram lo cambia, un 400/404 frena el scaneo como `ClientOutdated` y sugiere correr `tools/probe_feeds.py --only instagram` para elegir otro.

   **instaloader ya no hace ningún pedido.** Sólo queda su CLI para sacar la sesión de un navegador de verdad (`instaloader --load-cookies firefox --sessionfile ~/.config/instaloader/session-<usuario>`), y el bot lee ese archivo —un dict de cookies en pickle— directo. Se sacó del medio porque su manejo de fallas era justo lo que había que esquivar: reintentar contra un servidor que ya dijo que no, dormir adentro de un thread cuando creía que había que esperar, y ante una ficha de perfil fallida disparar una búsqueda extra para sugerir cuentas parecidas. Con la home tampoco hace falta resolver ids de perfil ni el caso ambiguo de «esa cuenta no existe» (que Instagram contestaba igual para una cuenta borrada que para una sesión muerta): la sesión muerta ahora se ve sola, como redirect al login o `login_required`.

   **Las fallas se tratan al revés una de la otra** (`_check()` en `instagram_api.py`): `checkpoint_required`, `challenge_required`, `feedback_required`, `login_required`, un `checkpoint_url`, un redirect al login o a un challenge, una página HTML en vez de JSON o un 401/403 significan que Instagram **acusó a la cuenta** (`AccountFlagged`): eso no se arregla esperando, y cada pedido que mandemos mientras tanto le confirma lo que ya sospecha. El scaneo se apaga y **se queda apagado hasta que un humano corra `!instagram reanudar`** — a propósito no hay reintento automático, porque el bot no puede saber si alguien entró a la cuenta a resolver el checkpoint. Un 429, el "Please wait a few minutes", un `spam: true` o un 5xx son `Throttled`: frenó pero no acusó a nadie, backoff y un solo aviso por episodio. Una excepción de red es `Unreachable` y sigue al ritmo normal. Un 400/404 o una home que no trae `feed_items` o trae posts que no se pueden leer son `ClientOutdated`. Las clases viven en `integrations/social_errors.py` y son las mismas para X.

   El estado va a **Mongo** (`instagram_state`, vía `SocialStateDAO`, el mismo DAO que usa Twitter con su propia colección), no a memoria: la única verdad es lo que hicimos nosotros, y **un bot que se reinicia y vuelve a leer como si nada después de un checkpoint es exactamente la forma de perder la cuenta**. `IG_USER_AGENT` tiene que tener el User-Agent del navegador del que salieron las cookies — cookies de Firefox viajando con un User-Agent de Chrome es una contradicción que se ve del otro lado.

   El comando **`!instagram`** muestra todo esto en `#robot-devil`: última lectura, próxima vuelta, backoff, qué vio la última home (cuántos posts, cuántos de la tabla, cuántos nuevos, y qué cuentas fuera de la tabla aparecieron) y el historial de frenadas. **`!instagram detener [motivo]`** frena el scaneo a mano y **`!instagram reanudar`** lo despierta — los dos usan el mismo freno que el bot se pone solo. El freno a mano no es un lujo: la advertencia de comportamiento automatizado te llega a vos por mail o por la app, y el bot recién se entera cuando Instagram ya le cortó el acceso. Frenar apaga el `tasks.loop` de verdad (`cancel()`); cuando el freno lo pone el propio bot, el loop se apaga con `stop()` —está adentro de su propia vuelta—. Después de un reinicio el loop arranca igual, da exactamente una vuelta, ve el freno en Mongo, avisa por qué no hay posts y se apaga: esa única vuelta es el precio de que el aviso exista.

   **Lo que no se va a ir solo no se reintenta.** Es la regla de `integrations/social_errors.py`, igual para las dos redes: sólo `Throttled` (429, 5xx, límite de follows) y `Unreachable` (red del Pi) vuelven a intentar solos. `AccountFlagged` y `ClientOutdated` frenan el scaneo hasta un `reanudar` a mano, porque el mismo pedido va a rebotar igual dentro de seis horas, y mandarlo una y otra vez —sobre todo con una sesión vencida— es de lo más marcable que hay. `AccountFlagged` además separa la **sesión vencida** (`session_dead`: X 32/89/239/353/401, el login en `x.com/home`; Instagram `login_required`, 401, redirect al login, HTML en vez de JSON; o directamente no hay archivo de sesión) del resto (checkpoint, bloqueo, suspensión, Cloudflare): el freno guarda de qué tipo fue (`blocked_kind` en Mongo: `session`, `account`, `outdated` o `manual`) y, si fue por sesión, **`reanudar` se niega mientras el archivo de sesión en disco no sea más nuevo que el freno** (`SocialStateDAO.stale_session`), porque reanudar ahí es mandar otro pedido con las cookies que ya rechazó. `reanudar forzar` lo saltea. Con el freno puesto tampoco salen los pedidos que dispara un humano (el follow de `!nuevo_*`), y si uno de esos pedidos encuentra la cuenta marcada, frena el scaneo igual que una vuelta.

   **La tabla y los seguidos tienen que coincidir**, en las dos redes: como sólo se lee la home, una cuenta de la tabla que la cuenta del bot no sigue nunca aparece. Por eso **`!nuevo_twitter` y `!nuevo_instagram` siguen la cuenta desde la del bot y recién después la anotan**, guardando el id numérico que devuelve la plataforma en `account_id` (X: `UserByScreenName` + `POST /i/api/1.1/friendships/create.json`, lo que hace el botón de la web; Instagram: `web_profile_info` + `POST /api/v1/friendships/create/<id>/`). El orden es a propósito: si la plataforma dice que la cuenta no existe (`TargetMissing`), no queda en la tabla por un typo. Si no se pudo seguir por algo pasajero, o el scaneo está frenado, se anota igual y el aviso pide seguirla a mano. **`!seguidos_twitter`** y **`!seguidos_instagram`** (`bot/commands/seguidos.py`) listan la tabla de cada red desde Mongo —a quién tiene que seguir la cuenta del bot—, sin pedirle nada a la plataforma.

6b. **Torneos de ajedrez** (`bot/scheduled/chess_check.py`, 1h loop): lee de la API pública de Lichess (`integrations/lichess.py`, sin token) las arenas y los suizos de los equipos de `LICHESS_TEAM_IDS` que todavía no arrancaron (`status=created`). Son dos equipos que no se parecen en nada: `ca-independiente-torneos` es el de los torneos abiertos que organiza el club (`ajedrez-cai`, una arena blitz por mes, ingreso libre al equipo), y `club-atletico-independiente` es el equipo cerrado del club (hay que pedir entrar y que un líder acepte), que casi no tiene torneos propios: lo inscriben en las batallas de equipos de las ligas que organizan otros clubes. **Lo que importa mostrar es quién puede jugar**, así que cada torneo se marca abierto o cerrado según el flag `open` del equipo, leído de la API en cada vuelta y no escrito a mano; cerrado con batalla de equipos es "Liga", cerrado sin batalla es "Interno". La marca va en todo lo que se ve: prefijo del nombre del evento (🟢/🔒), tipo de torneo en la descripción ("Torneo Abierto" / "Torneo de Liga", más el link para sumarse al equipo en los abiertos) y titular del anuncio. Si un torneo aparece en los dos equipos gana el abierto, porque por ahí se entra sin pedir permiso. Por ahora abiertos y cerrados usan la misma portada (`assets/banners/cai-chess.jpg`, ver Pendientes). Por cada torneo se crea un **evento externo** de Discord, con el link al torneo como ubicación —se juega en Lichess, no en un canal de voz—, anunciándolo en `#announcements`. A diferencia de los partidos, el evento **no se busca por nombre**: los torneos semanales repiten nombre, así que la colección `chess_tournaments` guarda id de Lichess → id del evento. Si cambia algo del torneo (hora, ritmo, duración) se edita el evento y se avisa; si un torneo agendado deja de figurar como "por arrancar" y su id da 404, Lichess lo borró (así se ve un torneo cancelado) y se borra el evento. Si alguien borra el evento de Discord a mano, el bot no lo recrea. El suizo no tiene duración fija: el fin del evento se estima como rondas × (los dos relojes enteros + 40 jugadas de incremento + 1 min entre rondas). `EventEndForumPoster` saltea los eventos con ubicación en lichess.org para no abrir un foro "post-partido"; `EventLifecycleManager` ya ignoraba los eventos sin canal de voz. No se espeja en Google Calendar. La portada es JPG y en 2,5:1, la proporción de portada de un evento de Discord: el logo original es un PNG cuadrado y un recorte al centro se comía la pieza y el texto, así que se rellenaron los costados con el rojo del fondo.

7. **Minecraft status** (`bot/scheduled/minecraft_check.py`, 1min loop): consulta el server de Minecraft por Server List Ping (`integrations/minecraft.py`, vía `mcstatus`) a través de la VPN de WireGuard y mantiene un único mensaje "banner" editado en `#minecraft` con si está prendido y quién está jugando. El ID de ese mensaje vive en `MINECRAFT_STATUS_MESSAGE_ID` (no en Mongo); si no está seteado, el bot crea uno nuevo y loguea el ID para que se persista a mano en el `.env`
8. **Music agent** (`bot/listeners/music_agent.py`): listens on `MUSIC_TEXT_CHANNEL_ID`; translates natural-language requests into Jockie Music commands via DeepSeek API; executes them by sending messages as a proxy user account (`NOT_ROBOT_DEVIL_USER_TOKEN`); moves the proxy user to/from the requester's voice channel to make Jockie follow along
9. **Hardware monitor** (`bot/scheduled/hardware_monitor_check.py`, 1min loop): consulta un agente HTTP standalone (`hwmonitor_agent/`, corre en la PC de Minecraft, no en el bot) vía `integrations/hardware_monitor.py` a través de la VPN de WireGuard, y mantiene un banner editado en `#robot-devil` con CPU/RAM/disco/uptime/temperaturas de esa PC (forénsica de los cuelgues de hardware que sufre esa máquina). A diferencia del banner de Minecraft, cuando la PC no responde el banner **no se edita** (queda mostrando la última performance conocida antes de la caída) y en su lugar se postea un mensaje de alerta aparte (`messager.hardware_monitor_alert`) con esas últimas métricas; otro mensaje avisa cuando vuelve. El estado (online/offline, último snapshot, último heartbeat, historial de caídas) se persiste en la colección `hardware_monitor` vía `HardwareMonitorDAO`, así sobrevive reinicios del bot. El **último heartbeat** es la última vez que la PC contestó `/metrics`: el footer del banner lo muestra (clave, porque el banner queda congelado mientras la PC está caída), el aviso de caída dice hace cuánto fue, y el aviso de vuelta lo usa para calcular el downtime cuando el bot se reinició estando la PC abajo. El agente también reporta el Kernel-Power Event ID 41 más reciente del Event Log de Windows (apagado no controlado), que el banner resalta si es reciente.

   El mismo scheduler monitorea la **red** en dos tramos, porque el bot llega a esa PC **siempre por el túnel de WireGuard** (aunque las máquinas estén en la misma red local, no se asume nunca el camino LAN):
   - **Internet de la PC**: lo mide el agente en un thread aparte cada 30s y lo cachea en el campo `network` de `/metrics` — latencia/jitter/pérdida contra un host público, latencia contra el router (para separar "se cayó internet" de "se cayó la red local"), tiempo de resolución DNS, tráfico en curso y un test de velocidad de bajada periódico. Todas las latencias se miden con handshakes TCP, no ICMP (sin permisos especiales ni parsear `ping.exe`).
   - **Túnel de WireGuard**: lo mide el bot (`hardware_monitor.measure_vpn_link()`) pegándole 4 veces al endpoint liviano `GET /ping` del agente, para no contaminar la medición con el tiempo que tarda en armarse `/metrics`.

   Cuando internet se cae pero la PC sigue respondiendo, se postea un aviso aparte (con 1 chequeo de gracia para no avisar por un microcorte) y otro cuando vuelve; los microcortes y la lentitud no generan aviso pero quedan registrados en Mongo (`kind: "network_degradation"`) y el banner muestra cuántos hubo en las últimas 24 h.

### Key Patterns

- All DAOs follow: `insert()`, `get_*()`, `exists()`, `upsert()`, `update_*()` — raw PyMongo, no ORM
- Adding a new command: create file in `bot/commands/`, add `await bot.load_extension('bot.commands.filename')` in `bot/client.py`
- **Alcance de un comando**: por defecto solo se puede usar en `#robot-devil`. Para habilitarlo en otros canales se declara en el decorador: `@commands.command(name="x", extras={"channels": (settings.GENERAL_TEXT_CHANNEL_ID, ...)})` (o `ANY_CHANNEL`, como `!ayuda`). Los permisos van aparte, con los checks de siempre (`@commands.has_permissions(...)`). `!ayuda` lista la **intersección** de las dos cosas: los comandos habilitados en el canal donde se pregunta y que además el que pregunta tiene permisos para correr (`filter_commands` corre los checks), así que un comando bien declarado aparece y desaparece de la ayuda solo
- Adding a new scheduled task: create file in `bot/scheduled/` with a `setup(bot)` function that adds a cog with `start_scheduled_job()`; load it in `client.py` and call `start_scheduled_job()` in `on_ready()`
- Discord channel IDs are env vars loaded via settings object on `config/settings.py` and accessed through the messager
- **Logging**: all errors and warnings in async code must use `await messager.log(msg, level="CRITICAL"|"ERROR"|"WARNING", exc=e)` — it posts to `ROBOT_DEVIL_TEXT_CHANNEL` and also calls the standard Python logger (visible via `journalctl`). Only use `logger.*` directly in sync helper methods where `await` is not possible. Messages should be written in first person, informally but informatively — e.g. `"No pude scrapear Olé"`, `"Le di el rol X a Y"`, `"No tengo permisos para..."` — not bureaucratic passive constructions.

## Environment Variables

All defined in `config/settings.py`. Required vars are also validated at startup in `main.py`. Key ones:

- `DISCORD_TOKEN`, `GUILD_ID` — Discord auth
- `DATABASE_URL`, `DATABASE_USERNAME`, `DATABASE_PASSWORD` — MongoDB
- `USER_AGENT` — HTTP user-agent string for scrapers
- `X_USERNAME` — cuenta de X con la que se leen los tweets (opcional; si falta, el scaneo de Twitter no corre). Sus cookies van en `~/.config/diablo-robot/x-session-<usuario>.json`, generadas con `tools/x_session.py`; `X_USER_AGENT` — el User-Agent del Firefox del que salieron (vacío = `USER_AGENT`)
- `IG_USERNAME`, `IG_PASSWORD` — cuenta de Instagram del bot; la sesión se lee de `~/.config/instaloader/session-<IG_USERNAME>` (`IG_PASSWORD` sigue validándose en `main.py` pero ya no se usa); `IG_USER_AGENT` — el User-Agent del navegador del que salieron las cookies de la sesión (opcional; vacío = el default de instaloader)
- `DEEPSEEK_API_KEY` — DeepSeek API key for the music agent (optional)
- `LICHESS_TEAM_IDS` — equipos de Lichess cuyos torneos se agendan como eventos, separados por coma (default `ca-independiente-torneos,club-atletico-independiente`; vacío = no se agendan)
- `GOOGLE_CALENDAR_ID`, `GOOGLE_SERVICE_ACCOUNT_FILE` — calendario donde se espejan los partidos y ruta al JSON de la service account que lo escribe (ambos opcionales; si falta alguno el espejo no corre)
- `NOT_ROBOT_DEVIL_USER_TOKEN`, `NOT_ROBOT_DEVIL_USER_ID` — Proxy user account used by the music agent to send Jockie commands as a real user
- `DJ_COMMAND_PREFIX` — Jockie Music command prefix (default: `m!`)
- Channel IDs: `GENERAL_TEXT_CHANNEL_ID`, `ANNOUNCEMENTS_TEXT_CHANNEL_ID`, `CLUB_TEXT_CHANNEL_ID`, `PRESS_TEXT_CHANNEL_ID`, `COMMENTATOR_TEXT_CHANNEL_ID`, `GAMES_TEXT_CHANNEL_ID`, `ROBOT_DEVIL_TEXT_CHANNEL_ID`, `MUSIC_TEXT_CHANNEL_ID`, `MINECRAFT_TEXT_CHANNEL_ID`
- `MINECRAFT_SERVER_HOST`, `MINECRAFT_SERVER_PORT` — cómo alcanzar el server de Minecraft dentro de la VPN de WireGuard (default `e-cai.mc:25565`); `MINECRAFT_STATUS_MESSAGE_ID` — ID del mensaje-banner en `#minecraft` que el scheduler edita en vez de recrear (opcional; si falta, el bot crea uno y loguea el ID a mano)
- `HARDWARE_MONITOR_HOST`, `HARDWARE_MONITOR_PORT` — cómo alcanzar el agente de hardware (`hwmonitor_agent/`) en la PC de Minecraft dentro de la VPN de WireGuard (default puerto `8788`); `HARDWARE_MONITOR_TOKEN` — token compartido enviado como header `X-Auth-Token` (debe matchear `HWMON_TOKEN` del agente); `HARDWARE_MONITOR_STATUS_MESSAGE_ID` — ID del mensaje-banner en `#robot-devil` (opcional; mismo mecanismo manual que `MINECRAFT_STATUS_MESSAGE_ID`)
- `GENERAL_VOICE_CHANNEL_ID`, `TERMOS_VOICE_CHANNEL_ID`, `IDLE_VOICE_CHANNEL_ID` — Voice channels used for events and proxy user idle state
- `GAMES_CATEGORY_ID` — Category ID for game channels
- `FOOTBALL_FORUM_ID` — Forum channel for match discussion

## Pendientes

- **Refactor de `influencers`: una persona, varias redes.** Hoy cada documento es una cuenta en una red (`name` + `platform`), así que la misma persona en Twitter, Instagram y YouTube son tres filas sin relación, y su "mirá mi último video" llega tres veces: el video, el tweet que lo anuncia y el post de Instagram. La idea es un documento por persona —nombre, fuente (`official`/`press`) y una entrada por red con su usuario y su id numérico (`{"twitter": {...}, "instagram": {...}, "youtube": {...}}`)—, que además ordena el relevamiento de gente multiplataforma.
  - **Comandos**: `!nuevo_influencer <nombre> <fuente>` crea la persona; `!vincular <nombre> <red> <usuario>` le suma una red y hace el follow automático que hoy hacen `!nuevo_twitter`/`!nuevo_instagram` (seguir antes de anotar, guardar el id); `!influencers` lista todo con sus redes y reemplaza a `!seguidos_twitter`/`!seguidos_instagram`.
  - **Migración**: no se puede unir solo, porque los usuarios no coinciden entre redes. Una persona por cada documento actual, y un `!fusionar <a> <b>` para juntarlas a mano.
  - **Deduplicación entre redes**, en dos capas. Por link, determinística: si el post apunta a algo ya relevado (el video de YouTube que ya está en `news`), se saltea; necesita normalizar URLs (`youtu.be/<id>` = `youtube.com/watch?v=<id>`) y en Instagram sirve poco porque los links casi nunca están en el texto ("link en bio"). Por contenido: la misma persona publicando casi el mismo texto en otra red dentro de unas horas; sólo es posible con el modelo unificado, guardando una huella de los posts recientes de cada persona.

La diseña el usuario; mismo formato que la actual: JPG en 2,5:1, la proporción de portada de un evento de Discord.
